# Agent Note: Legal child-chunk granularity is a per-KB choice

Status: proposed

## Problem

The deployment ingests 29,957 documents into one knowledge base whose
`kb_chunk_cap` is 1,000,000 child chunks. Measured with the audit script
(`--mode full --sample 2000 --seed 11`, stratified by "has articles / has none")
and extrapolated to the corpus:

| Policy | Estimated child chunks | Dense vector footprint |
|---|---|---|
| Article split by 款 (today) | **2.88 M** | 11.8 GB |
| Article split by 款, after version selection | 1.99 M | 8.2 GB |
| One child per article | **1.19 M** | 4.9 GB |
| One child per article, after version selection | **0.82 M** | 3.4 GB |

Only the last row fits the cap, and the deployment is green-field: there is no
existing data, so changing granularity costs nothing to re-ingest — it only has
to be decided before the first load. The corpus concentrates the problem in one
class: 地方法规 are 25,285 of 29,957 documents but 2.58 M of the 2.88 M chunks
(89.6%).

## Decision

`LawsChunker` takes a `child_policy` (KB config key `law_child_policy`):

- `paragraph` — split each parent block by paragraph, so a 款 is its own
  retrieval unit. This is the pre-change behaviour and stays the **default**.
- `article` — one child per article; `enforce_size_limits` still splits children
  longer than `child_chunk_size` (450 characters) on sentence boundaries, so long
  articles keep fine-grained retrieval. This is the intended end state:
  `article` + version selection lands at 0.82 M chunks and fits the cap with
  about 18% headroom.

The switch is implemented and unit-tested. The **deployment** default is
`article`: the legal knowledge-base bootstrap writes
`law_child_policy: "article"` when it creates the global KB
(`auth/bootstrap.py`). `LawsChunker`'s own code default stays `paragraph`, so
other callers and the audit script keep their previous behaviour.

Children are the units that embedding, BM25 and rerank actually score, so coarser
children dilute a single-款 match inside a long article. That quality trade-off
cannot be settled with the evidence available today — the plan defers the eval
set, and the development checkout has neither Milvus nor the remote
Embedding/Rerank services (`.env.example` only, nothing listening on 19530). The
choice therefore rests on capacity, and on the fact that the deployment is
green-field: nothing has been ingested, so the policy can be re-decided before the
first load at zero cost, and this note stays `proposed` until the A/B is run as
post-hoc validation.

The A/B procedure, once an environment exists: ingest a sample KB (the 2,184
national documents are enough and fit the cap under either policy) twice, once
with each policy; build a small eval set of law queries with expected law +
article; run `app/scripts/evaluate_retrieval.py` against both; compare hit rate
before flipping the default.

## Alternatives considered

**Sharding the global knowledge base into 3–4 KBs.** Keeps `paragraph`
granularity and needs no chunker change, and `kb_chunk_cap` is per-KB by design.
Rejected for now because the cost lands on the retrieval contract and operations:
every search then runs the multi-source path (`mode` always `hybrid`, `trace`
always `null`), `_compute_source_top_k` returns `top_k * 3` per source while the
source count is ≤ 4, so the rerank pool doubles (30 → 60 at `top_k=5`), any one
shard failing degrades the response, the shard key itself is a new decision
(地方法规 alone is 89.6% of the volume, so a category split is unbalanced), and
uploads, backups and rebuilds become N-way.

**Raising `kb_chunk_cap`.** Zero code and zero contract change, and it keeps the
finest granularity. Rejected: 2.88 M vectors is about 11.8 GB of dense data
before sparse vectors, HNSW structures and 2.88 M PostgreSQL rows, and the cap is
a safety valve rather than a capacity target — raising it removes the protection
without changing the underlying cost.

**Ingesting in stages — national documents first, 地方法规 later.** The 2,184
national documents are 0.219 M chunks even at `paragraph` granularity, so this is
a zero-risk way to go live. Rejected as the primary decision only because it
defers the same question; it remains the recommended fallback if the A/B cannot
be run before launch.

**Keeping `paragraph` granularity and relying on version selection alone.**
Version selection is orthogonal and worth doing regardless (about 31% of article
lines), but on its own it leaves 1.99 M chunks — still twice the cap.

## Consequences

The chunker now has two code paths to maintain, and a misconfigured
`law_child_policy` falls back to `paragraph` with a warning rather than failing
ingestion or silently selecting a different chunker.

The deployment now lands at about 1.19 M chunks on the full corpus and 0.82 M
with version selection (the ingest list generated by
`audit_legal_metadata.py --ingest-list`), which fits `kb_chunk_cap` with about 18%
headroom. Nothing in this change alters existing behaviour for other callers: the
code default path is byte-for-byte the previous implementation.

## Testing

`tests/test_legal_metadata.py::TestLawsChunkerFallback` covers both policies on
the same two-article fixture (three children vs two), the invalid-value fallback
to `paragraph`, and that an over-long article is still split by
`enforce_size_limits` under the `article` policy.
