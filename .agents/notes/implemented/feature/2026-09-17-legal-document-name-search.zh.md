# Agent Note: 法条库文件列表的搜索框

Status: implemented

[English](2026-09-17-legal-document-name-search.md) | 中文

## Problem

文件列表原本只有三种收窄方式——文件夹、分页、效力状态——没有一种按名字找。全局法条库有
22,036 份文件，找某一部法只能一百条一页地翻、用眼睛读文件名。页面上已经有状态筛选标签和
视图切换，缺的就是「敲几个字把文件找出来」这个最基本的入口。

## Decision

`GET /api/knowledge-bases/{kb_id}/documents` 增加可选参数 `q`，按**文件名**做不区分大小写的
子串匹配（`ILIKE %q%`）。

- **按文件名，而不是子块里的 `law_name`。** 列表展示的是 `law_name`（取首个子块的元数据），
  所以按它匹配也是理所当然的选项。先量了再定：抽样 500 份文档，法名都是文件名的子串，
  **500/500**——存在的差异只是 `…条例(2).docx` 这类重名后缀，法名依然包含在里面。反过来按
  `law_name` 匹配，就变成每行去 chunks 的 JSON 列里查一次（整表扫一遍就是 22k 次子查询）；
  按文件名匹配是对 `documents` 的一次顺序扫描。
- **用户输入里的通配符要转义。** `%`、`_`、`\` 在拼模式前先变成字面字符（`ESCAPE '\'`）。
  搜索框的语义是「文件名里含这几个字符」；不转义的话，搜 `办法_` 会悄悄变成通配匹配。
- **不为它建索引。** `%…%` 用不上 b-tree 索引，而两万多行顺序扫描是毫秒级；trigram 索引
  是为一个本来就很快的查询引入扩展和写放大，不值。
- **空白即不过滤。** `q` 先 trim，空串或纯空白不加条件，调用方可以直接把输入框的原值传下来。

前端把搜索框放在工具栏里、效力状态标签旁边：

- 防抖 300ms——列表是服务端过滤 + 无限滚动的，每敲一个字发一次请求会让分页状态反复重建、
  边打字边跳；
- 关键字进 query key，改条件即重启分页（两种筛选的结果页永远不会拼在一起）；
- **搜索时隐藏文件夹**——文件夹来自另一个接口、没有名称匹配语义；继续列出来既像「关键字没
  生效」，又会让 `totalItems` 不为零，把「没有匹配」的空状态顶掉；
- 空态区分「没有匹配「X」的文件」与「暂无文档」，并给一个清空按钮。

## Alternatives considered

**在前端筛已加载的页。** 否决：服务端分页下已加载的只是前缀，后面的匹配看不见，`total` 与
用户所见不一致，「一直往下滚总能找到」这条路悄悄断掉。

**连子块里的 `law_name` 一起匹配。** 按实测否决（见上）：文件名已经覆盖，子块查询贵一个数量级
而收益为零。

**给 `filename` 建 trigram 索引。** 否决：为了把毫秒级查询做得更快，引入一个扩展和每次写入都要
维护的索引。

**文件夹也跟着筛。** 暂不采纳：文件夹是导航，语料里的文件都平铺在根目录，一个「文件夹名匹配、
里面的文件不匹配」的结果是死路。将来文件夹真的装法条文件时，再专门重新考虑。

**给关键字单开一个端点。** 否决：它就是同一个查询上的一个条件；另开端点等于把分页、排序、权限
判定再写一遍。

## Consequences

多一个可选查询参数；不传 `q` 的请求与之前完全一致，包括响应结构。`q` 与 `validity_status`、
分页可以叠加（三者是 AND 关系）。

按名字找一个文件从「手工翻页」变成「一次扫描」——这在全局库上最明显，在只有几份文件的个人库里
则无所谓，同一个搜索框服务两处。
