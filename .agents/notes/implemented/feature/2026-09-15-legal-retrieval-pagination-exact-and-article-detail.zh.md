# Agent Note: 检索分页、法条精确检索与法条详情端点

Status: implemented

## Problem

PRD《法条检索基础API》功能清单里有三项没做，其中一项是实际使用暴露出来的、而不是读 PRD 读出来的。

**F-006 分页**没有任何参数，而响应里的 `total` 是"本次返回了几条"——看起来像命中总数，其实不是。
向量召回走的是有上限的候选池，本来就不存在一个可报的"总命中数"。

**F-002 法条编号精确检索**此前只是"按语义问一句、看运气"。在测试环境用
`“景德镇制”陶瓷保护条例 第六条` 实测：

```text
top1  第六条       score 0.7457  rerank 1.0598
top2  第二十六条   score 0.7093  rerank 1.0569
top3  第十六条     score 0.6689  rerank 1.0461
```

要的只有第一条，而邻条在结构上就无法区分：`第六条` 是 `第二十六条`、`第十六条` 的**子串**，
所以 BM25 会命中它们；又因为它们是同一部法的条文，稠密路由看起来也几乎一样。rerank 分差只有
0.3%，**任何阈值都分不开**——链路里现成的 `rerank_threshold`（默认 0.2）在这个量级上根本不会触发。

**F-201 根据法条ID查询法条详情**没有端点，尽管每条检索结果里已经在下发 `article_id`。

**F-105 地方性法规优先展示**实现成了过滤，而 PRD 写的是"优先展示"。两种做法都能过 PRD 的验收项，
所以先得把措辞定下来才能写进文档。

## Decision

**分页是排序列表上的一个窗口。** 新增 `page`（默认 1），与既有 `top_k` 配合：服务端取
`page × top_k + 1` 条候选、切出本页，并返回 `page` / `page_size` / `has_more`。多取的那一条让
`has_more` 是**事实**而不是猜测——请求最后一页会拿到 `has_more=false`，而不是"可能还有"。
`total` 保持原语义，文档里明确写清。窗口上限 **100**（`page × top_k` 超过即 400），因为 rerank
候选池本身有上限（`rerank_candidate_k` 默认 50）：承诺一个 20 条池子的第 5 页是撒谎。

**精确模式是"定位"而不是"排序"。** `match_mode` 接受 `semantic`（默认）与 `exact`。`exact` 会从查询
里解析出「法名 + 条号」（中文或阿拉伯数字、带不带书名号都认），再按元数据定位：先全等
`law_name`，不中再用"以输入结尾"（`民法典` → `中华人民共和国民法典`），并且始终限定
`article_number`。命中结果带 `mode="exact"` 与 `routes=["exact"]`。解析不出条号、或库里没有这一条时，
**退回 semantic 并在 `fallback_reason` 里说明**——静默降级正是 `law_levels` 那个坑的成因。
未知的 `match_mode` 一律 400。

**详情端点把两级 chunk 拼成一条法条。** `GET /api/legal/articles/{article_id}` 拆开
`{doc_id}:{article_number}`、定位文档，返回父块的正文作为 `content`（条文全文）、命中的子块作为
`matched_content`。法条元数据只挂在子块上、父块没有，所以两者都要——这段逻辑现在是
`retrieval/article_lookup.py::load_article_rows`，与精确模式共用：同一个"这条法条在哪"有两套实现，
恰恰是这套代码反复踩到的坑。

**读授权收敛成一个函数。** `authorize_content_read` 从 `api/retrieval.py` 的私有 helper 提到
`auth/kb_scope.py`，这样详情端点不可能比检索松——边界只改了一边，就会变成"检索查不到、详情却读得到"。

**F-105 定为过滤。** PRD 别处都写"筛选"（F-003、F-004、表 4 备注），它自己的验收项在两种读法下都过，
所以保留过滤，并把它写进文档成为有意语义，而不是既成事实。

**检索测试页打的就是集成方打的那几个接口。** 这个页面原先打 `/api/retrieval/test`，现在改打
`/api/retrieval/search`，并加了一个能力切换器，选项与真实接口一一对应：关键词检索与精确检索都是
POST `/api/retrieval/search`（只差 `match_mode`；exact 会忽略 `mode`/`top_k`，所以界面上把它们藏起来），
法条详情是 GET `/api/legal/articles/{article_id}`。界面上直接显示当前调用的路径；exact 未命中时的
`fallback_reason` 也会如实展示，不吞掉。两条检索路径今天**恰好**是同一份实现——测试页若依赖这个
巧合，等哪天它不成立时就什么也证明不了。

**页面的库选择器改成了多选，并且固定发 `kb_ids`。** 接口一直收列表、拿到多个时走多源联合召回，
但页面只能选一个库——于是集成方依赖的那条行为，恰恰是页面复现不了的那一条。现在可以勾任意多个，
而且**不论勾一个还是五个都发 `kb_ids`**，载荷形状不随数量变化。（全局法条库仍由服务端并入，所以
只勾一个个人库时走的就已经是多源路径。）那条路径**完全不看 `mode`**，所以当实际检索源多于一个时，
页面把「直接检索 / 混合检索」置灰，并在旁边写一句「多源固定混合」——摆一个服务端从不读的开关，
比不摆更糟。

**结果里把详情接口要的 `article_id` 露出来。** 两种检索能力都在 `metadata` 里返回它，可页面上
法名、条号、日期、状态都显示了，唯独没有这一个——想用详情接口只能去翻原始响应。现在每条结果都
渲染这串 id：点它直接切到「法条详情」能力查那一条，旁边还有复制按钮。

## Alternatives considered

**用相关性阈值代替精确模式**（加 `min_score`，或暴露既有的 `rerank_threshold`）。按实测否决：
前三名的 rerank 分差 0.3%，任何能去掉邻条的阈值会把答案一起去掉。而且阈值在这里根本帮不上忙——
召回接口刻意关掉了链路里的软阈值（`apply_rerank_filter=False`），其默认值 0.2 也远低于这些分数。

**精确模式做成"语义召回之后再过滤候选"**。否决：保留了"有没有恰好召回它"这个失败模式，候选池一旦
漏掉该条，就会对一条明明存在的法条报"找不到"。解析条号再查元数据是确定性的。

**让 `total` 承诺给出命中总数**。否决：有上限池上的 ANN 召回不存在有意义的"总数"。给出**探测出来的**
`has_more` 才是诚实的契约，`total` 保持既有语义、向后兼容。

**详情端点用空数组表示修订历史 / 关联司法解释**。否决：语料里这两类数据都没有（数据缺口三项中的两项），
空数组会被读成"这条法条恰好没有"，与"本服务答不了这个问题"是两回事。

**详情端点复用检索结果**。否决：该条文可能不在候选池里，而且会把本可拿到全文的位置换成截断的
`matched_content`。

## Consequences

检索响应新增五个字段（`page`、`page_size`、`has_more`、`match_mode`、`fallback_reason`），全都带默认值，
既有调用方不受影响；`tests/test_retrieval_contract_baseline.py` 同步更新——钉住响应信封本来就是它的职责。

新增 `api/legal.py` 路由与 `article_lookup.py` 模块，`main.py` 注册路由。检索侧的私有
`_authorize_and_boundary` 已删除，改由 `auth/kb_scope.authorize_content_read` 承担。

这三个端点的逐字段集成参考写在
[`docs/legal-retrieval-api.md`](../../../../docs/legal-retrieval-api.md)（入参/出参表、
`law_levels` 枚举映射、`metadata` 字段表、状态码与调用示例）。该文档已对着运行中服务的
OpenAPI schema 逐项核过：文档里的字段都存在，schema 里的字段也没有漏写。

精确模式会忽略 `law_levels` / `province` / `city`：条号已经唯一确定那一条，再叠过滤只会把命中变成
未命中。这一点写进了字段描述与接口手册。

**尚未验证的部分。** 精确模式与详情端点的 SQL 路径只在"生成的 SQL"与"路由注册"这一层验证过——
这个工作环境里没有数据库。`metadata->>'article_number' = '16'` 与 `law_name` 的全等/`LIKE` 回退都能正确
编译成 PostgreSQL，也与 pipeline 写库的方式一致（数字按 JSON 数字存、`law_name` 挂在子块上），
但**没有对真实库执行过**。部署新镜像后应在测试环境实测这两条路径，以及「`top_k=1` 对比 `exact`」
在真实「法名+条号」查询上的效果。

F-103（仅返回现行有效）**按决定不实现**（2026-09-15）。`validity_status` 的枚举由上游数据源
定义，而那份定义拿不到——文档里只有一个不带标签的整数（29,957 份全部来自
`source_code=national_laws`），所以按本项目"原始数据里没有的就不做"的约定，宁可丢掉也不猜。
从语料反推的读法（`3` 现行有效、`4` 尚未生效、`2` 已被修订、`0` 已废止、`1` 疑似失效、
`-1` 未标注）记在入库核对清单里**仅供参考**，明确不属于任何契约。因此 PRD 表 4 的"法条内容
校验"能力保持为 `/search` + `top_k=1` 的一种用法，不再单独开端点——它唯一的区别特征就是
时效过滤，而那条已经出局。

## Testing

`tests/test_legal_retrieval_api.py`（24 项）钉住了：查询解析（中文/阿拉伯数字、带不带书名号、
没有条号的情况）、分页窗口算术与切片（含最后一页与超上限拒绝）、未知 `match_mode` 返回 400、
`article_id` 拆分（含格式错误），以及新路由与全部新增请求/响应字段确实出现在 OpenAPI schema 里。
检索契约基线测试按信封扩展同步更新。连同相邻的检索、地域、loader 套件，共 **177 项通过**。

`frontend/src/pages/Retrieval.test.tsx` 钉住页面与这些接口的接线：每个能力交给 API 层的请求参数
（语义带 `mode`/`top_k`、精确只带 `match_mode`、详情按 `article_id` 且不要求选库），以及详情响应
能正确渲染；多选两个库时 `kb_ids` 两个都带上；点结果里的 `article_id` 会用它去调详情接口。
将来若有人悄悄把页面改回私有路径，测试会失败。前端测试全部通过，`npm run build` 通过。
