# Agent Note: 检索默认排除已废止与已失效的法条

Status: implemented

## Problem

两个问题在这里交汇。一是库里明知含有"已不具法律效力"的文档：22,036 份入库清单里
**2,581 份是已废止（`1`）**、**36 份是已失效（`-1`）**，合计 11.9%。没有默认过滤时，查一个
已被废止法条覆盖过的话题，可能把废止文本当作现行规定返回。

二是 PRD 的 F-103（"仅返回现行有效"）此前正因为拿不到枚举定义而被搁置：文档里只有一个不带
标签的整数，29,957 份全部来自 `source_code=national_laws`。记录"原样下发、不解释"那条决定的
note 是
[`2026-09-14-legal-result-metadata-exposure.md`](../architecture/2026-09-14-legal-result-metadata-exposure.zh.md)，
其中写明 `validity_status` 未被解释、需要该语义的消费方自行判断；
[`2026-09-14-legal-version-provenance-fields.md`](../architecture/2026-09-14-legal-version-provenance-fields.zh.md)
同样以"定义只能靠猜"为由否决了解释该值。**该定义后来从数据源自己的字典里拿到了**，那条前提
不再成立，本 note 取代它。

## Decision

枚举为：`3` 现行有效 / `2` 已修改 / `1` 已废止 / `-1` 已失效 / `4` 尚未生效 / `0` 未标注。

检索现在**默认排除 `1` 与 `-1`**。请求新增 `include_invalid`（默认 `false`）用于放开，
响应新增 `filtered_invalid_count`，让调用方知道"为什么这一页少了"。

边界是有意划的：

- **只排除"已不具法律效力"的那两个值。** `0`（未标注）绝大多数是决定类文件——2,031 份里
  1,844 份是 `law_type=修改、废止的决定`，它们本身是有效文件；`4`（尚未生效）是即将生效的
  版本。静默丢掉任何一个，都会拿掉调用方真正想要的答案。
- **取不到 `validity_status` 视为有效。** 读不到一个字段，和"这条法条失效了"不是同一个陈述；
  存疑时 API 返回该条。
- **只过滤语义召回。** `match_mode=exact` 与法条详情是"点名要那一条"的路径，仍然返回已废止的
  法条，状态照旧放在 `metadata` 里。把它们也过滤，会把一次有意的查询变成令人困惑的
  `404`/回退。
- **入库不变。** 指示很明确：入库不受影响，过滤属于查询时而不是入库时。保留全集同时也保住了
  "问当时的法律是什么样"的能力，这也是后续不必回头在入库侧再动一次的理由。
- 过滤发生在**召回之后**，因为 `validity_status` 还不是 Milvus 标量字段。因此 API 按约 4 倍
  放大候选量（已废止占比约 12%）让一页通常能凑满；当某次查询的候选池大多落在废止文本上时，
  返回仍可能少于 `top_k`。真正的预过滤要把该字段加进集合，那需要重建。

## Alternatives considered

**入库时就排除这 2,617 份。** 否决：指示明确是"入库不受影响"，而保留这些文档保住了"回答行为
发生时法律是什么样"的能力。它还能省约 12% 容量，所以这个选项留在桌上——如果哪天那个需求
消失。

**把过滤留给调用方。** 否决：默认口径会一直是错的（法律检索把废止文本当现行法返回），而且每个
集成方都要对着一个裸整数重写同一个谓词。

**连 `2`（已修改）和 `4`（尚未生效）一起排除。** 否决：`2` 是 159 部法在库里**实际能拿到的
最新版本**，排掉等于让这些法从库里消失；`4` 是即将生效的法，调用方有权现在就问它。

**现在就把 `validity_status` 加成 Milvus 标量字段。** 暂缓而非否决：那才是长期正确做法
（真预过滤、分页精确），但必须重建集合，而重建不能和正在跑的全量入库撞车。它是下一个重建
窗口的天然搭档。

**用状态白名单参数代替布尔开关。** 记为后续项。它是"只要 `3` 现行有效"需要的（布尔表达不了），
但布尔已经用单个字段覆盖了已定口径，接口面等真有调用方提再长。

## Consequences

响应信封新增 `filtered_invalid_count`；契约基线测试随之更新（与分页字段那次一样）。

对任何"依赖已废止法条出现在结果里"的调用方，这是**默认行为变更**，需要显式传
`include_invalid=true`。枚举也不再"未被解释"，所以上面链接的两份 note 在这一点上被取代——
API 仍然原样下发整数，但它的含义现在是记录在案的，不再留给调用方去猜。

入库侧选版规则（同法名组内优先 `validity_status == 3`）此前依赖同一个未确认的假设；已确认的
定义把它从猜测变成事实。那里仍未解决的是少量源库自身不自洽的记录——0.7% 的组有两条 `3`、
0.3% 的组里 `2` 比 `3` 新——而不是取值的含义。

## Testing

`tests/test_legal_retrieval_api.py` 钉住了谓词（只有 `{1, -1}`，六个取值逐个断言）、缺值视为
有效、请求默认即过滤，以及新请求字段与新响应字段都出现在 OpenAPI schema 里。

本地栈实测 A/B，用一份真实已废止的法条（《宁夏回族自治区执行〈中华人民共和国婚姻法〉的补充
规定》，`validity_status=1`）：

```text
查询「宁夏…补充规定 结婚年龄」默认口径      → top-5 全是现行有效的《国籍法》，已废止那份一条未出，filtered_invalid_count=10
同一查询 include_invalid=true                → top-5 全是那份已废止文档，filtered_invalid_count=0
未标注(0) 的《宽甸…三部单行条例修正案》默认 → 正常返回（0 不在排除集里）
```
