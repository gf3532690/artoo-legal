# Agent Note: DocxLoader 容错：损坏的包声明与表格正文

Status: implemented

## Problem

语料核对发现 88 份文档（占 29,957 份的 0.29%）正文完好却无法入库：

- **51 份在 `Document(path)` 阶段直接失败。** 44 份在 `_rels/.rels` 里声明了
  `userCustomization/customUI.xml` 而该部件不存在（全部来自江西省的来源）；7 份因
  `.docm` 被改名成 `.docx`，主部件内容类型是 macro-enabled。
- **37 份能打开但取不到文字。** 整篇正文放在一张 Word 表格里，而 `DocxLoader` 只读
  `doc.paragraphs`，它不含表格内段落。最大的一份有 403 段、约 1 万字。
- **另有 1 份同样取不到文字**——《清远市城市市容和环境卫生管理条例》，整篇正文（49 条、
  9,769 字）放在文本框里（`w:drawing` → `w:txbxContent`），python-docx 的段落模型同样
  看不到。它是在表格问题修完之后、full 抽样仍报告"1 份文档零 chunk"时才暴露的。

按版本选版过滤后，其中 45 份是各自法条的现行版本——也就是 45 个法名会**在库里完全
不存在**，包含江西省的大批法规。51 份全部用真实 loader 复现过，没有误报。

## Decision

新增 `pipeline/loaders/docx_repair.py`，在内存里修包级声明：删掉目标部件不存在的内部
关联（法律库的 `javascript:` 等外部链接一律保留）、删掉指向缺失部件的内容类型声明、
把 macro-enabled 的主部件内容类型改回标准 WordprocessingML 类型。`DocxLoader._open_document`
先试 `Document(path)`，失败才用修好的字节重试一次——**原文件永不被修改**。修复记录通过
`LoadResult.metadata["docx_repairs"]` 暴露。

正文提取从 `doc.paragraphs` 改为按顺序遍历 body 子元素（`w:p` 与 `w:tbl`），并递归进入
嵌套表格。段落与表格文字落进同一条文本流、保持文档顺序，切分器照常按「第X条」切分；
整篇在表格里的法条因此变成普通的条文结构文档。
当这次遍历一无所获时，loader 退回 `docx_xml_text.paragraphs_from_bytes`，直接从
`word/document.xml` 取段落——粗一些，但覆盖 python-docx 无法建模的内容，包括文本框。

## Alternatives considered

**放弃这 88 份、人工剔除。** 否决：它们是整部法条，而且损失按省份聚集——不处理会让
江西省的库静默地不完整，而不是可见地缺一块。

**入库前把文件在磁盘上修好。** 否决：那会改动爬虫持有的源数据，并让重新入库依赖一个
前置修复步骤。改内存副本能让 loader 保持"只读"。

**只对"取不到文字"的文档读表格。** 否决：那会让文本提取依赖上一次提取的结果；而且普通
文档里的表格本来就是内容，此前是被静默丢弃的。

**保留 `doc.paragraphs`、不读表格。** 否决：这正是缺陷本身——`doc.paragraphs` 不含表格内
段落，而语料里有 37 份整篇正文都是表格。

**用裸 `id(cell._tc)` 去重合并单元格。** 实测否决：`cell._tc` 是 lxml 按需创建的代理，
代理被回收后 `id` 会被复用，于是不同行被误判成同一个合并单元格而整行丢弃。在
《吉林省个体工商户条例》（125 个单格行）上只留下第一行——5,288 字符里只剩 687 字符。
现在把代理对象保活，`id` 才可靠。

**把文本框那份文档当作可接受的损失。** 否决：那是一部完整的法条。XML 兜底约二十行，
且只在结构化遍历完全取不到文字时才触发，因此不会改变本来就能解析的文档的正文。

## Consequences

loader 现在对**每一份** `.docx` 都返回表格文字，且这是共享 loader：Artoo 的入库会看到
同样的变化。这是有意的——表格内容就是文档内容——但它会改变任何含表格文档的 chunk 文本，
所以核对的条数会小幅变动（全量条文行从 1,139,213 变为 1,141,002，无条文文档从 3,276
变为 3,227），核对的 `fast` 模式也不再剔除表格，以与 loader 保持一致。

`LoadResult.metadata["docx_repairs"]` 是新的 loader 元数据键；pipeline 会把 loader 元数据
透传为文档元数据，因此可用于排障，但不属于任何持久化契约。

XML 兜底刻意做成"全有或全无"：只在结构化遍历完全取不到文字时触发，所以"正文段落与
文本框混排"的文档仍会丢掉文本框那部分。合并两个来源被否决——在没有更强信号的情况下，
它会在常见文档上造成文字重复，风险大于收益。

自愈只覆盖声明层损坏。`word/document.xml` 本身损坏的文件仍然抛 `ValueError`，错误信息
同时给出原始异常与自愈后的异常。

## Testing

`tests/test_docx_loader_repair.py` 用 python-docx 造出真实 docx 再按语料的方式污染它：
健康包原样返回；悬空内部关联被删除而外部 `javascript:` 链接被保留；macro-enabled 主类型
被改写；两类损坏文档都能被 `DocxLoader` 加载并记录 `docx_repairs`。表格行为也钉住了：
「段落 → 表格 → 段落」的文档顺序、只有表格的文档、嵌套表格、合并单元格只出现一次、
60 行表格每一行都保留、以及只有文本框的文档能通过 XML 兜底取回。

对语料的验证：此前受影响的 89 份现在全部可加载且正文非空（44 份缺部件 → 307,502 字符 /
2,013 条，7 份 macro-enabled → 32,686 / 215，37 份表格正文 → 204,251 / 1,649，
1 份文本框正文 → 9,769 / 49），逐份结果表就在核对报告目录下的 `problem_documents.csv`。
2000 份 full 抽样里"产出完整 chunk 元数据"的文档从 1999 份变为 2000 份。
